Using RESTful APIs

Gary Mitchell

01/25/2021

What is an API?

In generic terms, an API is an Application Programming Interface. APIs have existed for decades, since long before the Internet, and the term API does not automatically imply accessing data from the Internet. In fact, if you create a .R file that defines one or more functions and share that .R file with a friend, technically you have given your friend an API.

Yet today, when many (if not most) people mention using an API, they are referring to accessing online data. In these instances, they are most often referring to a RESTful API.

RESTful APIs

Representational State Transfer (REST) is a standard that defines how computers can communicate (i.e. exchange data) over the Internet. Using RESTful APIs makes it relatively easy to obtain data programmatically. The benefits of doing so are obvious:

  • Easily access data regularly, including periodic updates
  • Eliminate manual processes, including data entry (and the errors associated with manual process)
  • Improve the timeliness of data.

Understanding RESTful APIs

RESTful APIs allow programmatic communication using standard HTTP transactions (i.e. GET, POST). A program constructs and sends a request in much the same way that a web browser (e.g. Chrome or Safari) constructs and sends an HTTP page request. In the case of a typical web server, the server obtains/constructs the requested page and returns the page (as HTML) to the requesting browser (which subsequently displays the page).

A RESTful API works similarly. The requesting program constructs a request that it sends via HTTP. The receiving server (the API) performs the requested action (usually retrieving data), and constructs and returns an HTTP response. This response will conform to the REST standard and contains information about the request status (e.g. success, etc.) and the response (i.e. data content).

The diagram below illustrates this process. In the center we see the API (which resides on a server somewhere on the Internet). The API acts as an intermediary between the back end system (e.g. a database) and the front end application. The API allows the front end application to be relatively ignorant about the back end system. In other words, the front end application doesn’t need to understand how the data is stored, what database management system (DBMS) is being used, or whether the data is even stored or dynamically constructed. The front end application need only understand the requests supported by the API and the structure of the responses returned.

Similarly, the back end system needs to know nothing about the hundreds (or even millions) of front end applications that will be making requests. It only needs to understand requests and construct responses in a single format understood by the API.

Today, the majority of applications accessing data via the Internet, as well as most web-based applications, rely on RESTful APIs. Of course, there are alternatives, some of which are gaining in popularity and adoption. However, we’ll focus on using RESTful APIs in this course because:

  • Most of the data you will want to access will be available using a RESTful API
  • Once you understand the use of RESTful APIs, learning others (e.g. GraphQL APIs) will be relatively straightforward.

What do we need to access a RESTful API?

Well, to start, we need to understand the request and response formats for a particular API. Then, we need support in our programming environment for sending/receiving HTTP requests and parsing the response.

Most programming environments today provide good library support for accessing RESTful APIs and Python is no exception. These libraries provide functions (and/or Classes) that encapsulate all of the technical details associated with sending and receiving API requests and responses via HTTP. In PYthon, we’ll use the requests package to:

  • send/receive HTTP requests
  • parse binary encoded payloads into JSON objects.

What is JSON?

JSON stands for Javascript Object Notation. It is a portable format for transferring data that originated with Javascript web applications. Many (most?) APIs use JSON to return their responses. Alternative formats include XML and related standards.

The example below shows a JSON representation of an employee list. JSON is a fairly verbose representation of the data because it includes defining tags (e.g. “employees”, “firstName”) intermixed with the data, and the tags must be repeated with every occurrence (so we see that “firstName” appears 3 times, once for each employee’s record).

Authorized API access

Many APIs require some form of authentication before they will accept and respond to queries. Unfortunately, there isn’t a lot of consistency across APIs:

  • Some require usernames and passwords, while others require unique API keys or tokens
  • There is little/no consistency in how these are specified in the request (e.g. key=…, api_key=…, token=…, rapidapi_key=…).

As a result, just accessing the API and getting an authenticated response can be a challenge. The good news is that once you are in, it is generally straightforward to refine your query to obtain the data you want.

A simple example

As a first example, let’s acquire some data about COVID-19 from a free online database. While there are many free sources of data available online, the quality/integrity of data from such sources should be considered with care. Additionally, the data obtained from such sources may be stale (i.e. not containing the most current data).

For our first example, we’re going to obtain data from a COVID-19 database using a RapidAPI API to obtain the data. The API can be used for free, but the data is current only through August 19, 2020.

RapidAPI provides a number of free APIs that can be used to pratice (and discover interesting things you didn’t previously know). You can find their available APIs at the link below. Some of these impose access restrictions relating to requests per month, results returned, etc., so they may not be ideal for a research project. But, they provide a great base of APIs for practicing your data acquisition skills.

A different API key is required for each of these APIs, and you can request/receive the necessary key(s) through their website (typical for free online APIs).

The first step in accessing an API is to import the requests and pandas packages:

import requests 
import pandas as pd

Next, we need to construct a query string. I like to do mine in pieces, and then construct the final query string. In this case I have already assigned my API key to a variable named apikey. I then assign the API URL to urlbase and construct my query (which is assigned to query)":

urlbase = "https://covid-19-data.p.rapidapi.com/report/totals?"
query = urlbase + "rapidapi-key=" + apikey

This particular API is very simple. The only argument I need to pass to the API is my API key. Here’s the resulting query:

## https://covid-19-data.p.rapidapi.com/report/totals?rapidapi-key=**************************************************

Looking at the query is instructive. We see that the call arguments are specified as key-value pairs following the question mark (the asterisks are placeholders for the API key). Preceding the question mark is the address of the API, i.e. it’s URI.

Now we’re ready to execute our query, which we do using the get function (provided by the requests package).

response = requests.get(query)

The first thing we’d like to do is understand a little bit more about the data we’ve obtained. A first step is using the type function to see what we’ve obtained:

We can see that there are quite a few attributes. However, at this point, we are most interested in the status_code and the content. The status_code tells us whether our query was successful (typically a 200 status_code indicates success) and the content holds our payload, i.e. the result of our query. Generally, the first thing we should do after executing the query is to check the status code:

if(response.status_code == 200):
  # do work for good queries - 200 is usually the status_code for a good query
else:
  # do work to handle the unsuccessful query

Once we know our query was successful, we’re ready to extract the payload. In its current binary encoded form, the payload isn’t directly usable. However, the requests Response object provides a convenient function to convert the binary encoded content into JSON (JavaScript Object Notation):

covid = response.json()

The resulting json object will most likely be a list or a dictionary, depending on the complexity and organization of the data. Let’s see for sure:

A More Extensive Example

We can use the OpenWeather API to obtain weather data for any location, specified by a latitude and longitute. Here I use separate variables for the API URL, latitude, longitude, and the apikey (variable owkey, not shown) to construct my query.

As before, I construct my query using a base URL and the query arguments. The API URL precedes the question mark (?) and the API arguments follow. However, in this case, we have multiple arguments (lat, lon, and appid). We will separate our multiple arguments with ampersands (&). The value of owkey was set previously. This example shows constructing the query using an fstring.


URLbase = "http://api.openweathermap.org/data/2.5/onecall?"

lat = 45.51
lon = -122

query = f'{URLbase}lat={lat}&lon={lon}&appid={owkey}'

Here’s the resulting query (API key shown as askterisks (*):

## [1] "http://api.openweathermap.org/data/2.5/onecall?lat=45.51&lon=-122&appid=********************************"

Finally, we’ll execute and print the type of the payload.


owres = requests.get(query)
owjson = owres.json()
print(type(owjson))

## <class 'dict'>

This query returns a great deal of information (which highlights the need to understand the API before attempting to use it). Here are the top-level keys in the response dictionary:

for k in  owjson.keys():
  print(k)
## lat
## lon
## timezone
## timezone_offset
## current
## minutely
## hourly
## daily
## alerts

Here’s the contents of the current entry in the dictionary:


print(owjson['current'])
## {'dt': 1618527617, 'sunrise': 1618492897, 'sunset': 1618541628, 'temp': 293.87, 'feels_like': 292.7, 'pressure': 1015, 'humidity': 27, 'dew_point': 274.22, 'uvi': 3.4, 'clouds': 2, 'visibility': 10000, 'wind_speed': 2.24, 'wind_deg': 41, 'wind_gust': 4.47, 'weather': [{'id': 800, 'main': 'Clear', 'description': 'clear sky', 'icon': '01d'}]}

Because each entry in the dictionary is another dictionary that holds the detailed weather data. We can access the individual values as follows:

visibility = owjson['current']['visibility']
temp = owjson['current']['temp']

print(f'visibility:  {visibility}')
## visibility:  10000
print(f'temperature: {temp}')
## temperature: 293.87

Notice this query produces a great deal of information, and also highlights the need to understand the API. For example, in this case it shows the temperature, 293.87, above 200 degrees. Of course, the temperature readings must be specified in degrees Kelvin because that is the only temperature metric that makes sense with numbers that high. But what about the visibility of 10000? Is that metric specified in feet, meters, or some other unit of measure? We must always take care to understand the data before we begin to interpret or analyze it. The best way to do that is to review the API documentation.

A Final Example

From the previous example, we know the weather at latitude 45.51 and longitude -122. But where is that? We can use the Google Mapping API to find out.

Here we construct and execute a query to find mapping information using the latitude and longitude from our previous example. The finished query looks as follows:

## https://maps.googleapis.com/maps/api/geocode/json?latlng=45.51,-122&key=***************************************
